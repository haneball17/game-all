# DNF 2012 台湾服与多客户端同步重设计调研

## 1. 结论摘要

- **DNF（Dungeon & Fighter / DFO）可以确认是一款基于 Windows 的 2D 横版动作网游**，核心体验是副本推进、房间制战斗、技能连招、组队与疲劳值消耗，而不是 3D 场景自由探索型 MMORPG。[Steam](https://store.steampowered.com/app/495910/Dungeon_Fighter_Online/)、[DFO Guide - Fatigue Points](https://www.dfoneople.com/gameinfo/guide/Start-Leveling%21/Basic-Leveling/Fatigue-Points)、[Wikipedia-地下城与勇士](https://zh.wikipedia.org/wiki/%E5%9C%B0%E4%B8%8B%E5%9F%8E%E4%B8%8E%E5%8B%87%E5%A3%AB)
- **没有找到可信的一手公开资料能直接证明“2012 台湾服 DNF 使用某个现成商业引擎名称”**。更稳妥的说法是：它是 **Neople 自研的 Windows 原生客户端体系**，长期带有典型老式 Win32 / DirectX 兼容包袱；这一判断与韩服官方在 **2025-10-30** 公告中仍需保留 **DirectX 9 客户端运行路径** 的事实一致。[韩服公告 2025-10-30](https://df.nexon.com/community/news/notice/2923515)
- **2012 台湾服更可能处于“70 级 / Season 3 前后，但尚未进入 2012-07-19 韩服《时间之门》阶段”的窗口期**。这是基于：
  - 次级来源记载台湾由游戏橘子代理并于 **2012-07-11** 停运；
  - 韩服官方页面可证 **2012-07-19** 已出现“Season 3 / 时间之门”相关内容；
  - 因此“2012 台湾服最终态”高概率早于韩服的 Time Gate/80 级时代。该点属于**高概率推断，不是一手证实**。[Wikipedia-遊戲橘子](https://zh.wikipedia.org/wiki/%E9%81%8A%E6%88%B2%E6%A9%98%E5%AD%90)、[韩服时间之门 OST 公告 2012-07-19](https://df.nexon.com/community/news/notice/4394)
- 你仓库当前的多客户端同步实现，本质是**为了兼容老 DNF 客户端可能混用的多条输入读取链路**，因此同时覆盖了 `GetAsyncKeyState`、`GetKeyboardState`、`RawInput`、`GetMessage/PeekMessage`、焦点 API 与 `DirectInput`。这不是“过度设计”这么简单，而是对旧客户端输入路径不透明现实的工程性兜底。
- **建议重设计，但不建议推翻“共享内存 + 被注入端执行”的大框架**。更好的方向是：
  - 保留 `ActivePid + Heartbeat + Profile` 这套控制面；
  - 将执行端重构为**分层输入适配器**；
  - 将“状态快照”和“输入事件流”解耦；
  - 用“观测到的输入路径”驱动策略选择，而不是长期对所有路径同时强改。

## 2. 外部事实调研

### 2.1 已证实：DNF 的基本形态

可以直接确认的事实：

- Steam 页面将 DFO描述为 **classic beat-em up 2D action game**，并标注为 **Action / Side Scroller / MMORPG / Co-Op** 等标签。[Steam](https://store.steampowered.com/app/495910/Dungeon_Fighter_Online/)
- DFO 官方 Guide 明确存在 **Fatigue Points（疲劳值）** 机制，普通地下城按“进入房间数”消耗疲劳值，疲劳值耗尽后无法继续进入地下城。[DFO Guide - Fatigue Points](https://www.dfoneople.com/gameinfo/guide/Start-Leveling%21/Basic-Leveling/Fatigue-Points)
- DFO 官方旧更新中可以确认长期存在 **Party / Raid / Dungeon** 组织结构，且副本推进、队长驱动、队伍状态同步是基础玩法的一部分。[DFO Update - Party System Changes](https://www.dfoneople.com/news/updates/221/System-Upgrade/Miscellaneous-System/Party-System-Changes)、[DFO Update - New Contents: Raid](https://www.dfoneople.com/news/updates/510/New-Contents%3A-Raid)
- 维基百科作为次级来源，也与上述一手资料一致：平台为 **Microsoft Windows**，类型为 **2D 横版 ACT / 多人在线游戏**，开发商为 **Neople**。[Wikipedia-地下城与勇士](https://zh.wikipedia.org/wiki/%E5%9C%B0%E4%B8%8B%E5%9F%8E%E4%B8%8E%E5%8B%87%E5%A3%AB)

### 2.2 已证实：DX9 兼容现实依然存在

韩服官方公告《11/13(목) DirectX 11 지원 사전 안내》写明：

- 公告日期：**2025-10-30**；
- 生效日期：**2025-11-13**；
- Windows 10 以上开始支持 **DirectX 11**；
- 同时为不适合 DX11 的环境准备了 **DirectX 9 版本客户端运行方式**；
- 官方明确表示使用 DX9 客户端“不会影响游戏利用”。

这条信息的重要含义不是“今天的 DNF 仍是 DX9 游戏”，而是：

1. **DNF 历史上长期存在 DX9 路径**；
2. **旧兼容链路直到 2025 年仍具有现实意义**；
3. 因此在讨论 2012 台湾服这类老版本客户端时，把输入/窗口/渲染路径按“老 Win32 + DX9 兼容包袱”来理解，是合理且保守的技术判断。

来源：[韩服公告 2025-10-30](https://df.nexon.com/community/news/notice/2923515)

### 2.3 2012 台湾服时间线：可证与不可证部分

目前能相对稳定拿到的公开资料如下：

- 次级来源记载：台湾最早由 **游戏橘子** 运营；其公司历史条目记录 **2012-07-11** 终止营运《地下城與勇士》。[Wikipedia-遊戲橘子](https://zh.wikipedia.org/wiki/%E9%81%8A%E6%88%B2%E6%A9%98%E5%AD%90)

### 2.4 关于“2012 台湾服版本框架”的谨慎判断

基于上面的时间线，可以给出**带置信度标记**的判断：

- **高置信事实**：2012 台湾服于 2012-07-11 结束旧代理运营；韩服于 2012-07-19 已进入“时间之门”阶段。
- **高概率推断**：2012 台湾服最终形态更接近 **70 级 / Season 3 前后**，而非正式进入 “Time Gate / 80 级” 之后的阶段。
- **无法公开证实**：没有找到足够可靠的一手公开资料，能直接给出“2012 台湾服客户端内部模块框架图、渲染引擎名、输入系统实现细节”。

因此，后续技术判断应该采用下面这种表达：

> **把 2012 台湾服理解为“Neople 旧世代 Windows 原生 2D 客户端的一支地区版本”，而不是强行认定为某个外部商业引擎。**

## 3. 从游戏机制反推客户端技术约束

### 3.1 玩法结构对输入系统的要求

DNF 的核心玩法是：

- 角色在 **2D 横版副本房间** 中推进；
- 依赖 **方向键/技能键/组合输入** 实时战斗；
- 支持 **队伍副本、Raid、队长驱动的队伍状态推进**；
- 同时存在快捷栏施法与接近格斗游戏风格的操作要求。  
  参考：[Steam](https://store.steampowered.com/app/495910/Dungeon_Fighter_Online/)、[DFO Guide - Fatigue Points](https://www.dfoneople.com/gameinfo/guide/Start-Leveling%21/Basic-Leveling/Fatigue-Points)、[Wikipedia-地下城与勇士](https://zh.wikipedia.org/wiki/%E5%9C%B0%E4%B8%8B%E5%9F%B0%E5%8B%87%E5%A3%AB)

这类玩法天然会放大以下输入问题：

- `KeyDown / KeyUp` 丢失会直接形成卡键；
- 后台窗口若失去焦点，真实输入可能被客户端主动忽略；
- 技能映射、连发、方向键状态与边沿事件都很敏感；
- 只靠“窗口消息转发”很难覆盖所有输入读取路径。

### 3.2 为什么旧 DNF 客户端大概率存在“多输入路径”现实

虽然没有官方公开源代码，但从 DNF 的年代、平台与兼容现实反推，以下判断是合理的：

- 旧 Windows 网络游戏常同时存在：
  - Win32 键盘查询（如 `GetAsyncKeyState` / `GetKeyboardState`）；
  - 消息队列读取（`WM_KEY*` / `WM_INPUT`）；
  - RawInput；
  - DirectInput；
  - 前台/焦点相关 API 判定。
- 2025 年韩服仍需保留 DX9 客户端路径，说明“旧输入/旧渲染/旧窗口语义兼容”不是已经完全消失的问题。[韩服公告 2025-10-30](https://df.nexon.com/community/news/notice/2923515)

因此，从工程决策角度看，**把 DNF 视为一个“输入链路不可简化假设”的旧客户端**，比把它当成“只需改单一路径”的现代统一引擎客户端更稳妥。

## 4. 本地项目现状机制拆解

### 4.1 控制端（GUI / Sync 模块）

控制端的核心是 `GUI/Modules/Sync/Core/SyncController.cs`，它负责：

- 通过 `WH_KEYBOARD_LL` 采集主控端真实按键；
- 用 `WindowManager` 判定当前哪个 DNF 进程是主控；
- 维护热键、自动暂停、物理键状态校准；
- 按 `KeyboardProfile` 生成同步方案；
- 将结果写入共享内存 `Local\\DNFSyncBox.KeyboardState.V2`。  
  相关文件：
  - `GUI/Modules/Sync/Core/SyncController.cs`
  - `GUI/Modules/Sync/Core/KeyboardHook.cs`
  - `GUI/Modules/Sync/Core/WindowManager.cs`
  - `GUI/Modules/Sync/Core/KeyboardProfile.cs`
  - `GUI/Modules/Sync/Core/SharedMemoryWriter.cs`

同步协议字段包括：

- `Flags`：Paused / Clear
- `ActivePid`：主控 PID
- `ProfileId / ProfileMode`
- `KeyboardState / EdgeCounter / TargetMask / BlockMask`

这部分设计本身是合理的：它把“谁是主控”“当前方案是什么”“目标键状态是什么”都统一抽象到了一个稳定的控制面。

### 4.2 执行端（Payload / SyncMod）

被注入的执行端 `Payload/modules/sync/SyncMod.cpp` 会：

- 打开共享内存，读取同步快照；
- 若 `ActivePid == 当前进程 PID`，则旁路，不做伪造；
- 否则在本进程内 Hook 多条输入链路并注入同步状态：
  - `GetAsyncKeyState`
  - `GetKeyboardState`
  - `GetRawInputBuffer`
  - `GetRawInputData`
  - `GetMessage/PeekMessage`
  - `GetForegroundWindow/GetActiveWindow/GetFocus`
  - `DirectInput8Create/CreateDevice/GetDeviceState`

这意味着当前方案不是“把按键发给从窗口”，而是：

> **让每个从端进程自己读同一份共享快照，然后在本进程内部把真实输入视图改造成“像是本窗口自己正在接收这些按键”。**

### 4.3 为什么当前实现会同时 Hook 这么多路径

这是当前实现最值得保留的认知资产：

- 它假设 **DNF 不是单一路径读输入**；
- 它假设 **后台失焦时，客户端会额外做前台/焦点/RawInput 语义判断**；
- 它假设 **映射模式与连发模式需要边沿计数、状态清理与 RawInput 重写配合**；
- 它假设 **只改 Win32 API 或只发消息都不够稳**。

从旧 DNF 客户端的技术画像看，这套假设是成立的。

## 5. 是否应该重设计

## 5.1 结论：应该，但不是推翻重来

建议：**重设计执行层，保留控制层。**

原因：

- 当前控制层（共享内存 + ActivePid + Profile + Heartbeat）抽象得不错；
- 真正臃肿的是执行层：所有输入路径长期同时硬改，逻辑逐渐变成“兼容性补丁堆”；
- 对旧 DNF 这类客户端而言，完全移除注入或完全改成窗口消息主导，反而会失去兼容优势。

因此更好的策略不是“换总架构”，而是：

> **保留共享控制面，重做输入执行面。**

## 6. 候选重设计方案评审

### 6.1 方案 A：保留共享内存，收缩为分层输入适配器（推荐）

#### 核心思路

保留现有：

- `ActivePid`
- `Heartbeat`
- `Profile`
- `KeyboardState / EdgeCounter / TargetMask / BlockMask`

重构执行端为三个层次：

1. **观测层**：识别当前客户端更依赖哪条输入链路；
2. **适配层**：只启用必要的 Hook 组合；
3. **策略层**：根据 `ProfileMode` / 映射 / 连发选择最小干预方案。

#### 优点

- 与历史 DNF 客户端最兼容；
- 可复用你现有协议和大部分状态机；
- 能把“全路径常驻 Hook”收敛成“按需启用”；
- 维护成本可明显下降。

#### 缺点

- 仍保留注入式执行模型；
- 仍需要持续维护多路径兼容。

#### 结论

**这是最现实、最适合本项目的路线。**

---

### 6.2 方案 B：控制面 + 事件流双通道

#### 核心思路

把同步协议拆成两部分：

- **控制面**：心跳、主控 PID、暂停、配置版本；
- **数据面**：输入事件流（按下/抬起/边沿/映射后的事件序列）。

也就是从“完整 256 键状态快照主导”改成“事件流主导，状态快照辅助”。

#### 优点

- 更适合映射、连发、复杂边沿语义；
- 更容易做录制、回放、诊断；
- 可以减少从端对整块状态快照的重复拷贝和解释成本。

#### 缺点

- 协议与执行层都会变复杂；
- 对 RawInput/DirectInput 的重放策略设计要求更高；
- 不适合作为第一步改造。

#### 结论

适合作为**中期演进方向**，不适合直接一步替换现有实现。

---

### 6.3 方案 C：窗口消息 / 线程消息主导（不推荐作为主方案）

仓库里已有 `KeySender.cs`，说明项目历史上考虑过向窗口或线程消息队列发 `WM_KEYDOWN/WM_KEYUP` 的路线。

但对 DNF 这类客户端，这条路通常不够稳，因为它无法天然覆盖：

- `GetAsyncKeyState`
- `GetKeyboardState`
- RawInput
- DirectInput
- 焦点/前台判定

#### 结论

可以保留为**诊断或极简兼容模式**，但不应成为主方案。

---

### 6.4 方案 D：去注入、纯外部同步（不推荐）

如果完全放弃“被注入端在本进程内部伪造输入”的思路，只靠外部窗口控制，通常很难稳定解决：

- 后台窗口不接收真实焦点输入；
- RawInput / DirectInput 读取不到同步态；
- 组合键、边沿、连发和卡键修复都难做干净；
- 兼容性会显著下降。

#### 结论

不建议作为主设计方向。

---

## 7. 推荐路线图

### 7.1 短期（推荐立即实施）

- **保留共享内存协议主架构**；
- 把执行端重构成：
  - Win32 查询适配器
  - RawInput 适配器
  - DirectInput 适配器
  - 焦点语义适配器
- 增加“路径观测日志”，先判定实际活跃输入路径，再决定启用哪些适配器。

### 7.2 中期

- 将同步协议拆成：
  - `Control/Heartbeat`
  - `InputSnapshot`
  - `InputEventStream`
- 映射、连发和 `Clear` 逐步改成事件流驱动，状态快照只负责兜底与恢复。

### 7.3 长期

- 形成“按客户端行为自动选择最小 Hook 集”的能力：
  - 若目标版本主要读 Win32，则不长期干预 RawInput/DirectInput；
  - 若目标版本明显依赖 RawInput / DirectInput，再逐步升级策略。
- 让 Sync 机制从“全覆盖硬改”变为“能力协商 + 最小必要干预”。

## 8. 对本仓库的直接建议

结合当前代码，建议保留并继续演进的部分：

- `Shared/Protocols/` 中的 Sync 共享协议思路；
- `SyncController` 的 `ActivePid + Heartbeat + Pause/Clear + Profile`；
- `KeyStateTracker` 的边沿计数与连发建模；
- `ActivePid == 当前进程` 的旁路逻辑。

建议重点重做的部分：

- `Payload/modules/sync/SyncMod.cpp` 的“大一统常驻 Hook 逻辑”；
- `Replace/Mapping` 对 `RawInput` 的耦合方式；
- 焦点伪造与输入伪造之间缺少“能力判定层”的问题；
- 观测与执行未分层，导致问题定位成本高。

---

## 9. 最终结论

如果目标是让这套多客户端同步机制在 **“类似 2012 台湾服那样的老 DNF 客户端形态”** 上长期可维护、可诊断、可扩展，那么：

- **不应推翻“共享内存 + 被注入端执行”的总架构**；
- **应当重构执行层，把它从“补丁堆”改为“分层输入适配器”**；
- **窗口消息方案只能当辅助，不应上升为主方案**；
- **事件流化是值得做的中期方向，但不应一步到位替换现有协议**。

换句话说：

> 对老 DNF 客户端而言，更好的方案不是“更外部”，而是“更分层、更可观测、更按需干预”。
