# 实机问题分析—同步延迟与方向键卡住

## 背景

在实际环境运行下，当前项目的 Sync 机制主要遇到两个问题：

1. 同步有些许延迟，且偶发性出现无法同步。
2. 长按或非常快速地点按方向键后停止按键时，主窗口 A 角色已停止，但同步窗口 B 仍会持续向某个方向移动；当鼠标点击同步窗口 B 使其重新获得焦点后，角色才会停止移动。

本文档仅记录本轮排查结论与后续修复方向，**不包含代码改动**。

---

## 本地代码排查结论

### 1. 控制端采集链路

当前控制端 Sync 采集主链路位于：

- `GUI/Modules/Sync/Core/KeyboardHook.cs`
- `GUI/Modules/Sync/Core/SyncController.cs`

现状要点：

- 使用 `WH_KEYBOARD_LL` 低级键盘钩子采集输入；
- 在 `SyncView` 生命周期中启动 `SyncController`；
- `OnKeyEvent()` 收到按键后立即更新 `_keyState` 并调用 `PublishSnapshot()`；
- 同时依赖 `HeartbeatTick()` 每 50ms 执行 `AlignKeyStateWithPhysicalInput()` 做补偿性修正；
- 当前 `SharedMemoryConstants.HeartbeatIntervalMs = 50`。

这意味着：

- 极快输入下，控制端并不是纯事件驱动，而是“**事件驱动 + 50ms 周期补偿**”混合模式；
- 如果 `KeyUp` 在极端时序下漏掉或晚到，就要等心跳线程补偿；
- 对方向键这种“持续移动 + 高频抖动 + 快速松手”的场景，50ms 已足以形成肉眼可见的不同步窗口。

### 2. 执行端同步链路

执行端主逻辑位于：

- `Payload/modules/sync/SyncMod.cpp`

现状要点：

- 所有从端进程读取同一份共享内存快照；
- 若 `ActivePid == 当前进程 PID`，当前进程旁路，不做伪造；
- 否则执行端会同时覆盖多条输入读取路径：
  - `GetAsyncKeyState`
  - `GetKeyboardState`
  - `RawInput`（`GetRawInputBuffer` / `GetRawInputData`）
  - `GetMessage/PeekMessage`
  - `GetForegroundWindow/GetActiveWindow/GetFocus`
  - `DirectInput GetDeviceState`
- 执行端还包含：
  - `snapshot cache`
  - `spoof delay`
  - `RawInput` 内部残留状态 `g_lastRawKeyboardState`
  - Win32 边沿状态 `g_lastEdgeCounter`

这说明当前实现不是“发消息给从窗口”，而是：

> 让每个从端进程在本进程内部读取共享快照，并把自己的输入视图改造成“像是本窗口自己正在接收这些按键”。

## 问题 1：同步延迟、偶发不同步

### 当前高概率原因

#### 原因 A：低级键盘钩子线程模型偏弱

当前 `WH_KEYBOARD_LL` 钩子由 GUI 生命周期触发安装，实际更接近运行在 UI 主线程语境中，而不是独立采集线程。

这会带来几个现实问题：

- 高频输入时，UI 线程上的其他工作会放大钩子回调抖动；
- 回调延迟会直接体现在共享快照写入延迟上；
- 极端情况下可能出现短时事件漏采或“事件到达晚于客户端内部读取时机”。

#### 原因 B：50ms 心跳补偿对方向键场景偏慢

`HeartbeatTick()` 当前是：

1. `AlignKeyStateWithPhysicalInput()`
2. `PublishSnapshot(forceClear: false)`

这会让“漏掉的 KeyUp / KeyDown”必须等到下一轮心跳才被纠正。普通技能键容忍度较高，但方向键与短促点按更容易受到影响。

#### 原因 C：执行端快照缓存与多路径分流会放大不同步窗口

执行端通过 `ReadSharedSnapshotCached()` 做线程局部缓存，不同输入路径：

- `GetAsyncKeyState`
- `GetKeyboardState`
- `RawInput`
- `DirectInput`

并不保证在完全同一个时间点读取到相同的新状态。

表现上就可能出现：

- 某一路已经看到最新释放态；
- 另一路仍拿着上一拍的按下态；
- 最终在实际角色行为上表现成“偶发不同步”或“慢半拍”。

### 当前判断

“同步有些许延迟、偶发不同步”更像是：

> **控制端采集不够强实时 + 执行端多路径读状态不完全同步** 的叠加结果。

## 问题 2：方向键卡住，点一下同步窗口 B 才停止

### 当前高概率原因

这是本轮排查中最明确的问题类型：

> **后台进程 B 的某条输入链路残留了“方向键仍按下”的内部状态，但共享同步状态实际上已经停止；当 B 真正获得焦点时，客户端内部输入状态被刷新，于是移动终止。**

### 为什么更怀疑 RawInput / DirectInput，而不是单纯 Win32

#### 1. 当前症状和“焦点刷新后恢复”高度相关

用户描述里最关键的一句是：

- 点击同步窗口 B 使其聚焦后，角色停止移动。

这更像：

- 客户端自己的焦点/输入状态机在重新获得真实前台语义时发生了刷新；
- 或者其设备态（尤其是 RawInput / DirectInput）被重新同步；
- 而不是单纯某个 Win32 API 返回值的问题。

#### 2. 当前代码已主动改写 RawInput 前后台语义

执行端当前存在：

- `FixWmInputMessage()`
- 对 `WM_INPUT` 的 `RIM_INPUTSINK -> RIM_INPUT` 修正

这本身就说明：

- 目标客户端很可能依赖 RawInput 的前后台语义；
- 后台输入在该游戏里并不是“天然等价于前台输入”。

#### 3. 非 Mapping 模式下，RawInput 的主动纠偏不够激进

当前在 `Hook_GetRawInputBuffer()` 中：

- `Mapping` 模式下会主动构造目标键序列；
- 但在非 Mapping 模式下，仅在以下情况强制改写：
  - `ShouldBlockKey(...)`
  - `targetMask[vKey] != 0 && (!alive || paused)`

也就是说，**正常同步过程中**，非 Mapping 模式不会持续把 RawInput 强制改成“共享快照期望状态”，更多是兜底式修正。

这就给“方向键释放未被某条 RawInput 路径及时消费”留下了空间。

#### 4. `g_lastRawKeyboardState` 是卡方向嫌疑点

当前代码中：

- `ApplyRawClearIfNeeded()` 只有在 `FlagClear` 时才清 `g_lastRawKeyboardState`；
- 正常同步过程中，如果方向键释放链路没有正确闭环，这个内部状态可能残留；
- 一旦客户端重新聚焦，真实输入状态/设备状态被刷新，移动终止。

### 当前判断

“方向键卡住直到点击 B 才恢复”更像是：

> **RawInput / DirectInput / 焦点语义联合问题**，其中 RawInput 残留态嫌疑最大，DirectInput 与焦点刷新是辅助因素。

## 联网资料对上述判断的支撑

### 1. 低级键盘钩子不是长期高负载输入同步的理想形态

Microsoft Learn 对 `LowLevelKeyboardProc` 的说明要点：

- 低级键盘钩子回调应尽快返回；
- 如果处理过慢，可能影响系统对钩子的调度；
- 官方明确建议在很多场景下优先考虑 **Raw Input**，而不是长期依赖低级钩子。

来源：
- `LowLevelKeyboardProc`  
  https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc

### 2. `GetKeyboardState` / `GetAsyncKeyState` 的语义本身并不等价

Microsoft 文档指出：

- `GetKeyboardState` 的状态与**线程消息队列**消费有关；
- `GetAsyncKeyState` 则是异步全局状态语义；
- 二者天然就可能在时序上不同步。

来源：
- `GetKeyboardState`  
  https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeyboardstate
- `GetAsyncKeyState`  
  https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate

这直接支持了本地代码中的判断：

> 只要执行端同时覆盖多条输入读取路径，就必须面对“不同路径在边沿时刻不完全一致”的问题。

### 3. Raw Input 明确区分前台与后台输入

Microsoft 文档对 `WM_INPUT` 明确区分：

- `RIM_INPUT`：前台输入
- `RIM_INPUTSINK`：后台输入

来源：
- `WM_INPUT`  
  https://learn.microsoft.com/zh-cn/windows/win32/inputdev/wm-input

这和本地 `FixWmInputMessage()` 的存在完全吻合，也解释了为什么：

- 后台同步窗口 B 的输入问题会和焦点状态高度耦合；
- 点击 B 获得真实前台后，客户端输入状态会重新收敛。

### 4. 前台/焦点语义仍会影响游戏输入行为

Windows 前台窗口与输入焦点的官方说明也支持这一点：

- 前台窗口线程会得到更高优先级；
- 键盘输入天然被定向到前台窗口；
- 应用程序是否把后台输入当作真正可用输入，取决于其内部实现。

来源：
- `SetForegroundWindow`  
  https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow

### 5. DirectInput 设备态会受获取状态影响

微软旧版 DirectInput 文档中，`GetDeviceState` 与设备获取状态关系密切，`DIERR_NOTACQUIRED` 也是常见异常路径。

来源：
- `IDirectInputDevice8::GetDeviceState`  
  https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417897(v=vs.85)
- `IDirectInputDevice8::Acquire`  
  https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417818(v=vs.85)

这支持了另一个观察：

> 即使 RawInput 是主嫌疑，DirectInput 在焦点切换后一起恢复，也完全合理。

## 当前优先级判断

### 对“同步延迟 / 偶发不同步”

优先级从高到低：

1. `WH_KEYBOARD_LL` 运行形态偏弱（更像 UI 线程采集，而非专用采集线程）
2. 50ms 心跳补偿过慢
3. 执行端 snapshot cache 与多路径读取时机不一致

### 对“方向键卡住直到点击 B 才恢复”

优先级从高到低：

1. 非 Mapping 模式下 RawInput 路径释放收敛不足
2. `g_lastRawKeyboardState` 残留按下态
3. DirectInput / 焦点恢复时才把内部设备态刷新
4. 主控端高速方向键时 `KeyUp` 漏采，而后续补偿不够激进

---

## 当前建议的修复方向（仅记录，不实施）

### 短期最小修复方向

1. 将键盘采集从 UI 生命周期中剥离，改为专用采集线程。
2. 对方向键的 `KeyUp` 引入更积极的发布与收敛策略，不再完全依赖 50ms 心跳。
3. 缩短或禁用方向键路径上的快照缓存，优先保证释放边沿实时性。
4. 增强非 Mapping 模式下对方向键 RawInput 的“期望态重写”，尤其是释放态。
5. 增加只针对方向键的链路日志，记录控制端采集、共享快照发布、RawInput/DI/Win32 各路径观察结果。

### 中期方向

1. 将执行端重构为分层输入适配器，而不是所有路径长期并行硬改。
2. 将“状态快照”和“输入事件流”逐步解耦，减少对全量键状态块的边沿依赖。
3. 为方向键、高频连点键建立单独的释放收敛与清键机制。

---

## 结论

当前两个实机问题都说明：

- 这套同步机制的总方向（共享内存 + 被注入端执行）仍然成立；
- 但“控制端采集强实时性”和“执行端多输入路径收敛一致性”已经成为主要稳定性瓶颈；
- 方向键卡住问题最像 **后台输入链路残留按下态**，其中 RawInput 残留与焦点恢复最值得优先处理。

现阶段更合适的动作不是推翻设计，而是：

> **在保留总架构的前提下，优先修复控制端采集线程模型、方向键释放收敛，以及执行端 RawInput / DirectInput 的边沿一致性。**
